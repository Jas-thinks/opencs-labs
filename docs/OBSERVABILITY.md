# Observability

This document is for the people operating the 12-node cluster. It covers metrics, dashboards, alerts and logs. The reasoning behind the choices is in [ADR-011](ADR/011-observability-and-ci-cd.md).

**Grafana:** <http://10.1.75.53:5305/grafana/>. The user is `admin`; the password is `GRAFANA_ADMIN_PASSWORD` in `deploy/distributed/secrets/cluster.env` on the operator machine. Everything runs on the campus network, and no data leaves it.

## Architecture

```
every node ── opencs agent (:9100 Host A, :6000→622X Host B; bearer token)
api1..4    ── app /metrics (:8000, bridge only, not public)
                    │  scrape every 30 s
                    ▼
pg2 (monitoring node, beside the PostgreSQL standby)
  VictoriaMetrics :8428   stores 30 days (-memory.allowedBytes=64MiB)
  vmalert         :8880   17 rules; firing state written back as ALERTS
  Grafana         :3000   served by the edge at /grafana/ (login required)
```

The whole stack (VictoriaMetrics, vmalert, Grafana, PostgreSQL standby and agent) uses about **125 MiB** of non-reclaimable memory on pg2, out of its 512 MiB. Each agent is about 15 MiB and needs only the Python standard library. Every service runs under the existing supervisor, and the watchdog restarts VictoriaMetrics or Grafana if their health checks fail.

### Why a custom agent

Standard exporters don't fit these targets:

- `node_exporter` reports the *host*: 120 CPUs and 125 GiB, rather than each container's 1 CPU and 512 MiB cgroup.
- There is no root, Docker or systemd for sidecars.

So [`node/agent.py`](../deploy/distributed/node/agent.py) reads the cgroup and the supervisor's PID files and logs directly. Each role adds its own metrics:

| Role | Metrics |
|---|---|
| all | `opencs_cgroup_memory_bytes{type=anon\|file\|limit}`, `opencs_cgroup_cpu_seconds_total`, throttling, PSI pressure, `opencs_cgroup_oom_kills_total`, disk free, `opencs_service_up{service}`, `opencs_service_restarts_total`, `opencs_log_errors_total` |
| edge | `opencs_edge_requests_total{area,status_class}`, `opencs_edge_request_duration_seconds` (histogram, includes upstream time), `opencs_edge_upstream_requests_total{upstream}`, all parsed from the buffered access log |
| pg1 / pg2 | `opencs_pg_up`, `in_recovery`, `connections{state}`, `replicas_streaming`, `replication_lag_bytes`, commits, rollbacks, deadlocks, cache hit ratio, size. On the primary only: `opencs_jobs{status}`, `opencs_oldest_pending_job_seconds`, unread notifications. Uses a read-only `opencs_monitor` role with `pg_monitor` |
| hub | `opencs_hub_up`, `opencs_hub_running_servers`, `opencs_hub_server_limit` |
| control | `opencs_backup_age_seconds` |

The API's own `/metrics` adds per-route request counts and latency (`opencs_http_*`), notebook launches, grader runs and process memory.

Log files are followed from their *end* when an agent starts. History is never replayed as new events, so counters start at 0. Restarts are counted from the supervisor's "restarting in" lines, which are written only on unexpected exits.

## Dashboards (folder "OpenCS", provisioned read-only)

| Dashboard | Answers |
|---|---|
| Cluster overview | Is anything firing or down? Memory, CPU, pressure, throttling per node; service status, restarts, error lines, disk, new OOM kills |
| Edge & API | Requests/s by area, status classes, backend spread, API and notebook latency (p50/p95/p99), slowest routes, 5xx per route, API RSS |
| Database, jobs & backups | Primary up, standby streaming, replication lag, connections, TPS, cache hit ratio, job outbox, oldest pending job, backup age |
| Notebooks | Running servers vs capacity per shard, hub health, shard memory, launch time p95 |

The dashboards are generated by [`monitoring/config.py`](../deploy/distributed/monitoring/config.py). To change one, edit the builder there, then run `deploy.sh config grafana`. UI edits are disabled, so the repository stays the source of truth.

## Alerts (shown in Grafana only, by choice)

| Alert | Condition |
|---|---|
| NodeAgentDown / APIDown | a scrape target is down for 2 min / 1 min |
| ServiceDown / ServiceFlapping | supervised service not running for 2 min / more than 3 restarts in 15 min |
| EdgeErrorRateHigh | more than 5 % 5xx for 5 min |
| APILatencyHigh | API p95 at the edge above 500 ms for 10 min |
| PostgresDown / ReplicationBroken / ReplicationLagHigh | PostgreSQL down, standby not streaming, lag above 64 MB |
| ConnectionsNearLimit | above 85 % of `max_connections` |
| MemoryPressure / OOMKill / DiskLow | anon memory above 90 % of the limit, a *new* OOM kill, less than 10 % disk free |
| JobBacklog | oldest pending job older than 10 min (the worker on ctl is stuck) |
| NotebookCapacityHigh / HubDown | above 85 % of notebook slots in use / a shard is down |
| BackupStale | the latest dump is missing or older than 26 h |

vmalert has no notifier (`-notifier.blackhole`). Firing alerts appear in the *Firing alerts* panel of the overview dashboard, from the `ALERTS` series. Counter-based rules use `x - x offset 15m` rather than `increase()`, so a series that has only just appeared, for example after an agent restart, can't fire falsely. To add a channel later (email, Discord, Slack), add an Alertmanager or point `-notifier.url` at one. The rules don't change.

## Logs

Logs stay on each node, in `~/opencs/logs/<service>.log`, with hourly size-based rotation by the watchdog. Search them from the operator machine:

```bash
D=deploy/distributed/deploy.sh
$D logs all                      # last lines of every log on every node
$D logs api api 'ERROR|Traceback'  # grep the API logs on the four API nodes
LINES_N=200 $D logs edge edge.access ' 5[0-9][0-9] '   # 5xx at the edge
$D logs pg2 grafana
```

The edge access log records the upstream, request time, upstream time and request ID for every request. The API echoes the same request ID (`X-Request-ID`), so one request can be followed across nodes.

## Operations

| Task | Command |
|---|---|
| First install / binaries / monitor role | `deploy.sh monitoring` (VictoriaMetrics, vmalert and Grafana are checksum-verified on the operator machine) |
| Change rules, scrape targets or dashboards | edit `monitoring/config.py`, then `deploy.sh config agent vm vmalert grafana` |
| Is scraping healthy? | Grafana → Explore → `up`, or `curl http://172.17.0.33:8428/api/v1/targets` from pg2 |
| Moving the monitoring node | change `tuning.monitoring_alias` in `inventory.json`, run `deploy.sh monitoring`, then `deploy.sh config` |
